LLM Microservices Deployment Lab

This README describes how to start the lab environment, deploy Kubernetes resources, and verify that the LLM microservice is running correctly.

- Start the Lab (Privileged Mode). The lab must be started in privileged mode:

sudo kathara lstart --privileged

1. Kubernetes Cluster Verification

- Verify that the Kubernetes cluster is up and running. On the controllers:
Controller1: VNI8000,VID800, 2.0.0.0/24 -> Deals worker11
Controller2: VNI9000,VID900, 1.0.0.0/24 -> Deals worker21 

- Split the terminal window:
kathara connect controller1
kathara connect controller2

- Check nodes:
kubectl get nodes


- Check that system pods are running:
kubectl get pods -A
watch "kubectl get pods -A"


2. Deploy Namespaces. On the controllers:

kathara connect controler1
kubectl apply -f /shared/clustera/ns.yaml

or

kathara connect controler2
kubectl apply -f /shared/clusterb/ns.yaml

- Verification: check all the NAMESPACES
kubectl get namespaces

3. Deploy PersistentVolumeClaim (Cluster A and B): on the controllers

- Deploy the PVC used to access the shared LLM weights:

kubectl apply -f /shared/clustera/pvc.yaml
or
kubectl apply -f /shared/clusterb/pvc.yaml

- Verification: CHECK DETAILS OF THE PVC
kubectl -n llm-ns get pvc

- maybe watch it, allthough Bound State is ok, you can see it was indeed created.
watch kubectl -n llm-ns get pvc

4. Create Services

- Deploy the Service resource exposing the microservice:

kubectl apply -f /shared/clustera/svc.yaml
or
kubectl apply -f /shared/clusterb/svc.yaml

- Verification: SERVICE TYPE IS CLUSTER IP
kubectl -n llm-ns get svc -o wide

- For later use: here you can check name, ns, ip, port, target port...
kubectl -n llm-ns describe svc

5. Deploy the LLM Microservice (Deployment)

- Create the Deployment for the LLM microservice:

kubectl apply -f /shared/clustera/deploy_llm.yaml

kubectl apply -f /shared/clustera/deploy_llm_rdma.yaml

or
kubectl apply -f /shared/clusterb/deploy_llm_rdma.yaml

- Verification (watch until ready): check ready, and the image
kubectl -n llm-ns get deploy -o wide
watch kubectl -n llm-ns get deploy -o wide

- Inspect the running Pods: they have a designatd worker, they are running, and they have an IP:    INFO PODS
kubectl -n llm-ns get pods -o wide

6. Inspect Services

- Get detailed information about a Service: INFO SERVICE DETAILED
kubectl -n llm-ns describe svc

7. Create Ingress

- Deploy the Ingress resource to expose the service via HTTP:

kubectl apply -f /shared/clustera/ing.yaml
or
kubectl apply -f /shared/clusterb/ing.yaml

- Verification: check the hosts names, and the port. INSPECT INGRESS
kubectl -n llm-ns get ingress -o wide

- Inspect the Ingress configuration in a more detailed way:
kubectl -n llm-ns describe ingress llm-ing

8. Testing the Microservice, from client_int

kathara connect client_int

- Send a test request to the /completion endpoint:

curl -X POST -H "Content-Type: application/json" \
-d '{"query":"An orc wanted to destroy everything"}' \
http://clustera.com/completion

or

curl -X POST -H "Content-Type: application/json" \
-d '{"query":"An orc wanted to destroy everything"}' \
http://clusterb.com/completion

- The response should be JSON containing a short story generated by the LLM, starting with the correct prompt.

9. Monitor the Deployment

- Continuously monitor all resources in the namespace:

watch "kubectl -n llm-ns get all -o wide"

- Troubleshooting

- check where ingress-nginx containers is running:

kubectl -n ingress-nginx get pods -o wide


10. Check RDMA: with the curls working...

- From controller1 -> name all the pods with -> llm-dply-7f477c78c4-xxxhh
kathara connect controller1
kubectl get pods -A

- From controller2 -> llm-dply-5d9fdf6455-6r9zg
kathara connect controller2
kubectl get pods -A

- From the client side, funny enough, here the controllers
- Verify that the RDMA connection is working (put some logging... I did not, only for errors): check the webserver logs 

- controller1
kubectl -n llm-ns logs llm-dply-CHANGES

- controller2
kubectl -n llm-ns logs llm-dply-CHANGES

- From the server side in this case llama_weights: connect to llama_weights to check the RDMA server logs: if no errors it is fine

kathara connect llama_weights

tail -f /var/log/server.log
